# Database business rules

This chapter lists the constraints and invariants that the schema and code enforce. Where a rule exists only in application code (not in MySQL) it is marked **App**; rules enforced by the database are marked **DB**.

## Data types and conventions

| Topic | Rule | Level |
|---|---|---|
| Primary keys | `bigint unsigned auto_increment` `id`; exceptions: `tenants.id` (varchar, tenant slug), `notifications.id` (char UUID), `platform_release_tenant` (composite PK), cache/session tables | DB |
| Money | `decimal(15,2)` (29 columns), `decimal(12,2)`, `decimal(14,2)`, `decimal(10,2)` for amounts; quantities use `decimal(10,2)`/`(10,3)`; coordinates `decimal(10,7)`; percentages `decimal(5,2)`. No floats | DB |
| Currency | `currency varchar(255)` default `'RWF'` on sale, expense and finance tables | DB |
| Status/type columns | All `varchar`; **no MySQL ENUM** exists anywhere. Allowed values are checked in FormRequests against `config/modules.php` | App |
| Timestamps | `created_at`/`updated_at` nullable timestamps on nearly all tables | DB |
| Soft deletes | Only `customers` and `employees` (`deleted_at`) | DB + models (`SoftDeletes`) |
| Generated columns | None (no `GENERATED` columns in the live schema); totals are stored columns maintained by services | DB |
| Business codes | Human codes such as `SL-YYYYMMDD-0001`, `MLS-`, `MET-`, `EGS-`, `ABD-`, `FT-` generated by `generate*Code()` helpers: prefix + date + 4-digit sequence from the last existing code (read-then-increment, **not** atomic) | App |

## Referential actions (live schema)

All 264 foreign keys are either `ON DELETE CASCADE` (158) or `ON DELETE SET NULL` (106); there are no `RESTRICT` rules.

| Pattern | Rule | Effect |
|---|---|---|
| `tenant_id -> tenants.id` | CASCADE (all 76 tables) | Deleting a tenant row removes all its data |
| `farm_id -> farms.id` on module tables (animals, livestock, flocks, feedings, milk sessions, sales, expenses, finance transactions, ...) | CASCADE | Deleting a farm deletes everything recorded against it |
| Header to child (`sale_transaction_id`, `milk_session_id`, `finance_transaction_id`, `breeding_record_id`, `abattoir_dispatch_id`, `customer_id` on customer sub-tables, `employee_id` on employee sub-tables) | CASCADE | Children vanish with the parent |
| Optional references (`animal_id`, `flock_id`, `livestock_id`, `customer_id`/`animal_id` on `sale_items`, `created_by`, `action_by`, `abattoir_return_id`, `milk_storage_id`) | SET NULL | History rows survive, losing the link |
| `users` referenced as `created_by` | SET NULL | Deleting a user keeps records |

> **Warning:** Because farms cascade to sale items, payments and finance transactions, deleting a farm removes financial history. Customers and employees avoid hard deletes through soft deletes. Check the controller before relying on deletes being blocked.

## Invariants enforced in code (App)

### Sales and customers

- Items may only be added to **draft** sales (`SaleTransactionService::addItem`); item type must match the sale type.
- Totals: `subtotal = SUM(sale_items.total_price)`; `total = max(0, subtotal - discount + tax)`; recomputed by `recalculateTotals`.
- Payment status derived: `total <= 0` -> unpaid; `paid >= total` -> paid; `paid > 0` -> partial; else unpaid. Not recomputed for cancelled sales.
- `completed` requires at least one item. `cancel` is refused for completed or cancelled sales. Payments are refused on cancelled sales.
- Animal sale: each animal must be `lifecycle_status = 'Active'` (case-insensitive) and belong to the sale's farm; an animal cannot be on two in-progress animal sales; on completion it becomes `Sold`. Abattoir dispatch additionally requires `health_status = 'Healthy'`. Per-kg pricing requires live weight and price per kg. Sick, Quarantined and Under treatment animals only trigger a UI warning (`Animal::SALE_WARNING_STATUSES`).
- Flock bird sale: flock must belong to the sale farm, quantity >= 1 and not above `flocks.current_count`; completion posts a `sale` flock event.
- Milk sale: `confirm` deducts stock from the selected storage tank (`deductForUnifiedSaleItem`) and creates/syncs a `milk_distributions` row (category `sold`); `cancel` removes the distribution. Confirm applies only to milk sales and needs >= 1 item.
- `customer_credit.outstanding_balance` is recalculated by `CustomerService::syncOutstandingBalance` after complete, confirm, cancel-related changes and payments.
- Sale numbers: `SL-` (animal), `MLS-` (milk), `MET-` (meat), `EGS-` (egg), dispatch `ABD-`.

### Finance (double entry)

- Posting happens through observers: `SaleTransactionObserver::updated` (when `sale_status` changes to `completed` posts revenue; `completed -> cancelled` posts a reversal), `SalePaymentObserver::created` (posts the payment), `ExpenseObserver::saved/deleting` (posts paid expenses; `paid -> void/draft` or amount change reverses and reposts; deleting a paid expense reverses it).
- Sale recognition: debit accounts receivable (1200) for gross; credit revenue (per `config/finance.php`: milk 4000, animal 4100, meat 4200, egg 4250) for net; credit taxes payable (2100) for tax. Expense: debit expense account (5000-5900 by category code, default 5900), credit cash.
- Sale payment (`posting_kind = collection`): debit cash, credit accounts receivable.
- A posting is skipped when the same `(source_module, source_type, source_id, posting_kind)` exists; a reversal is created at most once (DB unique key + code check).
- Posting date selects an accounting period (`FinancePeriodService::forDate` creates a monthly period if missing); **posting is refused when the period status is not `open`** (`InvalidArgumentException`).
- Amounts of zero or less are not posted.
- `FinanceAccount` rows with `is_system = true` are shared by all tenants; `requireAccount()` fails when a required account code does not exist.

> **Warning:** `FinanceAccountResolver::cashAccount()` chooses the bank account (1100) only when the payment method is in `config/finance.php` `bank_payment_methods` (`bank_transfer`, `mobile_money`, `cheque`, `card`), but expenses and sale payments are validated against `config/modules.php` `expense_payment_methods` (`Cash`, `Mobile money`, `Bank transfer`, `Cheque`, `Other`). The strings differ in case and spacing and the comparison is strict, so every posting is credited/debited to the **cash account (1000)**; the bank account is never used. Verify before relying on cash vs bank reports.

### Inventory ledgers (feed, medicine, milk storage)

- Quantity must be > 0; movement type must be one of the configured values; outbound movements that would make the balance negative throw "Insufficient ..." (`recordMovement`, inside `DB::transaction`).
- Milk storage uses `lockForUpdate()` on the tank row; feed/medicine ledgers store the resulting `balance_after`/quantity per movement. Milk outbound types: sale, adjustment_out, spoilage, distribution; all others add.
- Milk storage status is recalculated: `maintenance` is sticky; otherwise quantity <= 0 -> `available`, quantity >= capacity -> `full`, else `in_use`.
- Medicine consumption for treatments and dewormings is refused when the medicine is expired or inactive (`is_active = false`); editing or deleting a treatment restores/re-syncs stock (`restoreForTreatment`, `syncForTreatment`, and equivalents for dewormings). Feed consumption is refused for inactive feed types; feedings sync with the inventory (`syncForFeeding`).
- `feed_inventories` has one row per `(farm_id, feed_type_id)` (`ensureInventory`).

### Poultry

- `FlockService::adjust` clamps `current_count` at zero (`max(0, count + quantity)`), sets `lifecycle_status = 'Sold'` when it reaches zero while active, and writes a `flock_events` row with `balance_after`. Mortality, cull, sale and adjustments all go through this method.
- One egg collection per flock, day and shift (DB unique).

### Milk production

- One milk session per herd (livestock), date and shift (DB unique; code catches the duplicate and throws "A milk session already exists for this herd, date, and shift.").
- One record per animal per session; only eligible animals (lactating production status, or per `isMilkingEligible`) may be added; sessions must be editable (open); session totals are recomputed after each record change (`recomputeTotals`).
- `MilkRecordObserver` and `ExpenseObserver` invalidate the cost-per-litre cache for the farm/date.
- Distributions: category `sold` is managed only from Sales and cannot be edited or deleted in the Milk module; manual distributions deduct from and return to storage.

### Breeding

- Female must be a female animal; internal sire must be male; both must belong to the farm; either an internal sire or an external sire name is required.
- Gestation days default per animal type from `config('modules.breeding_gestation_days')` to compute the expected delivery date.
- A breeding record with a birth cannot be edited; pregnancy-check date must be on or after the breeding date and cannot be added after birth; one birth record per breeding (DB unique), only for `pending` or `confirmed_pregnant` breedings, alive offspring cannot exceed total offspring.
- Registering offspring creates an `animals` row; stillborn offspring cannot be registered and an offspring cannot be registered twice. Pregnancy check results update the breeding status and the mother's status (`applyPregnancyCheckResult`).

### Users, tenants and access

- Registration creates the tenant, a `workspace_admin` user and the `tenant_accounts` row (see chapter 3).
- Inactive users (`is_active = false`) cannot log in and are logged out by `module.access`.
- Non-admin members need a `workspace_module_permissions` row per module; create/edit/delete also require `can_view`.

## Observers summary

| Observer | Model | Events | Effect |
|---|---|---|---|
| `SaleTransactionObserver` | `SaleTransaction` | `updated` | Post revenue on completion; reverse on completed -> cancelled |
| `SalePaymentObserver` | `SalePayment` | `created` | Post payment entry |
| `ExpenseObserver` | `Expense` | `saved`, `deleting` | Post/reverse paid expenses; invalidate milk cost cache |

Registered in `FinanceServiceProvider` and `MilkServiceProvider`. There are no `boot()` hooks other than the tenant `creating` hook in `BelongsToTenant`.

## Gaps and risks

- **Concurrency:** document code generators (`generate*Code`, `generateSaleNumber`) read the last code and add one without a lock; simultaneous requests in one tenant can produce a duplicate that the unique `(tenant_id, code)` key rejects with a SQL error.
- **Nullable `tenant_id`** on 69 of 76 tenant tables and nullable foreign keys everywhere (see chapter 3).
- **No CHECK constraints**: non-negative quantities, positive amounts and valid statuses are not enforced by the database.
- **Unused tables:** `finance_budgets`, `finance_budget_items`, `finance_tax_rates`, `finance_tax_entries`, `finance_balance_snapshots` exist but no code reads or writes them.
- **Legacy models** `Sale`, `MilkSale`, `MilkSaleItem`, `MilkSalePayment`, `MilkSaleLog` have no tables; `MilkSaleService` is unreachable.
- **`payment_status = overdue`** is a configured value but no code assigns it.
- **Bank vs cash posting** mismatch described above.
- **Cascade deletes** from `farms` and `tenants` remove financial records.
